# VPS·인프라 담당자 발표 예상 질문 & 모범답안 (Q&A 준비집)

> **대상**: ADA v2 발표 — **VPS·운영 인프라 담당자(나)** 의 예상 질의응답 대비.
> **범위**: 서버 구성 · Docker · 데이터 계층 · 네트워크/SSH 터널 · 보안 · LLM 인프라 · CI/CD · 관측성 · 백업 · 비용 · 실제 장애대응.
> **사용법**: 질문마다 **출제확률 · 중요도(★) · 우선순위 등급(S/A/B/C)** 을 표시했습니다. S부터 외우세요.

## 📐 채점·우선순위 기준 (먼저 읽기)

| 지표 | 의미 | 척도 |
|---|---|---|
| **출제확률** | 심사위원·동료가 실제로 물어볼 가능성 | 0~100% |
| **중요도(★)** | 못 답하면 타격이 큰 정도 | ★(1) ~ ★★★★★(5) |
| **우선순위 등급** | 준비 순서 | **S**=최우선 / **A**=높음 / **B**=중간 / **C**=여유 시 |

- **S 등급** = 출제확률 80%↑ **그리고** 중요도 ★★★★ 이상 → **반드시 암기·즉답**.
- **A 등급** = 출제확률 60%↑ **또는** 중요도 ★★★★ → 핵심 키워드 암기.
- **B 등급** = 보통 → 흐름만 기억.
- **C 등급** = 깊은 질문 → 키워드만.

> **점수 계산식(준비 점수)** = 출제확률(%) × 중요도(1~5) ÷ 100.
> 예) 90% × 5 ÷ 100 = **4.5점** → S등급. 0~5점 척도, **3.2점 이상이면 S·A.**

## 1. 아키텍처·서버 구성

### Q1. 전체 시스템 아키텍처를 1분 안에 설명해 주세요.
> 🎯 출제확률 **95%** · 중요도 ★★★★★ · 우선순위 **S** · 준비점수 4.8

**답변:** ADA는 **서버 2대**로 운영됩니다. ① **웹 서버(VPS, 클라우드)** — 공인 IP를 가진 임대 서버로, 사용자가 접속하는 사이트(nginx·FastAPI·Streamlit)와 데이터 계층(PostgreSQL·Redis·MinIO·MLflow), 분석 워커(Celery)가 돕니다. ② **로컬 서버(학원, 온프레미스)** — GTX 1060 GPU가 있어 로컬 LLM(Ollama)과 GPU 학습, 백업을 담당합니다. 두 서버는 **SSH 터널(autossh)** 로 연결되어, NAT 뒤에 있는 로컬 서버도 안전하게 통신합니다. 핵심 설계 철학은 **"비싼 건 안 쓰고, 무료부터 쓴다"** — 3-tier LLM(팀 KB → 로컬 Ollama → 클라우드 Claude)으로 비용을 최소화했습니다.

**한 문장 암기:** "공인 IP 웹 서버(VPS)와 GPU 로컬 서버를 SSH 터널로 묶고, 무료 우선 3-tier LLM으로 월 2~3만원에 운영합니다."

### Q2. 왜 서버를 2대로 나눴나요? 한 대로는 안 되나요?
> 🎯 출제확률 **90%** · 중요도 ★★★★★ · 우선순위 **S** · 준비점수 4.5

**답변:** **역할과 비용을 분리**하기 위해서입니다. ① 웹 서비스는 24시간 인터넷에 떠 있어야 하니 **공인 IP가 있는 저렴한 VPS**가 맞습니다(월 2~3만원, GPU 불필요). ② 반면 LLM 추론·모델 학습은 **GPU가 필요**한데, GPU VPS는 월 수십만 원이라 비현실적입니다. 그래서 **이미 보유한 학원 GPU 머신(GTX 1060)** 을 연산 전용으로 씁니다. 결과적으로 "**값싼 클라우드는 웹, 보유 GPU는 연산**"으로 나눠 **비용은 최소, 성능은 확보**했습니다. 한 대로 합치면 GPU 비용이 폭증하거나, 로컬만 쓰면 공인 IP·가용성이 없습니다.

### Q3. VPS 사양과 월 비용은? GPU가 없는데 LLM은 어떻게 돌리나요?
> 🎯 출제확률 **72%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.9

**답변:** VPS는 **GPU 없는 저사양(월 2~3만원)** 입니다. LLM은 VPS에서 직접 안 돌리고, **SSH 역터널로 학원 GPU의 Ollama에 연결**해 씁니다. 즉 VPS가 `localhost:11434`로 Ollama를 부르면 터널을 타고 GTX 1060의 Ollama가 응답합니다. 정말 똑똑한 답이 필요할 때만 클라우드 Claude(유료)를 호출하므로, VPS에 비싼 GPU가 필요 없습니다.

### Q4. 로컬(학원) 서버는 무엇을 담당하나요?
> 🎯 출제확률 **70%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 2.1

**답변:** 네 가지입니다 — ① **Ollama 로컬 LLM 추론**(qwen2.5:7b/coder), ② **GPU 학습 워커**(무거운 DL 학습을 Celery로 위임받음), ③ **로컬 백업**(VPS 데이터를 Pull 방식으로 받아 보관), ④ KB 일부 로컬 저장. 한마디로 **"GPU가 필요한 일 + 백업"** 전담입니다.

### Q5. 서버가 한 대 죽으면 서비스는 어떻게 되나요?
> 🎯 출제확률 **64%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.56

**답변:** **부분 장애로 버티도록(graceful degradation)** 설계했습니다. ① 로컬 서버가 죽으면 → Ollama·GPU 학습은 멈추지만, 웹·분석 기본 흐름은 **회로차단기**가 감지해 클라우드 Claude로 폴백하거나 해당 단계를 건너뜁니다. ② VPS가 죽으면 사이트는 내려가지만, **로컬 백업 서버에 데이터가 보존**되어 복구 가능합니다. 즉 한쪽이 죽어도 데이터 유실이나 전면 중단은 막도록 했습니다.

### Q6. 왜 직접 서버를 구축했나요? 관리형(AWS RDS 등)을 안 쓴 이유는?
> 🎯 출제확률 **55%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.65

**답변:** **비용과 학습 목적** 때문입니다. 관리형 서비스(RDS·ElastiCache 등)는 편하지만 월 비용이 큽니다. 우리는 **월 2~3만원 VPS + 보유 GPU**로 동일 기능을 자체 구축해 비용을 1/10 이하로 낮췄고, 인프라 전 계층(DB·캐시·스토리지·LLM·CI/CD)을 직접 다루며 운영 역량을 쌓았습니다. 대신 Docker·백업·회로차단 등으로 **관리형 수준의 안정성**을 코드로 확보했습니다.

## 2. Docker·컨테이너 오케스트레이션

### Q7. Docker로 무엇을, 어떻게 띄우나요?
> 🎯 출제확률 **85%** · 중요도 ★★★★★ · 우선순위 **S** · 준비점수 4.3

**답변:** 모든 서비스를 **docker-compose로 컨테이너화**했습니다. **profile(프로파일)** 로 묶음을 나눠 필요한 것만 띄웁니다 — ① `core`: postgres·redis·minio·mlflow·api·frontend·nginx·워커 ② `ml`: GPU 학습·산출 워커·serving ③ `sec`: Vault·보안 사이드카. 평소엔 `docker compose --profile core --profile ml up -d` 한 줄로 전체가 뜹니다. 컨테이너마다 메모리 상한·헬스체크·`restart: unless-stopped`를 걸어 죽으면 자동 재시작됩니다.

**암기 키워드:** "compose + profile(core/ml/sec)로 필요한 묶음만, 헬스체크 + 자동재시작."

### Q8. 컨테이너가 죽으면 어떻게 되나요? 무한 재시작 위험은?
> 🎯 출제확률 **65%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.6

**답변:** 각 서비스에 **`restart: unless-stopped`** 정책이 있어 죽으면 도커가 자동 재기동합니다. **헬스체크**(예: api는 `/health`, frontend는 `/_stcore/health`)로 "살아있는지"를 주기적으로 확인하고, 의존 서비스는 `depends_on: condition: service_healthy`로 **DB·Redis가 정상일 때만** 기동합니다. 무한 재시작(crash loop)은 헬스체크 `start_period`와 로그·운영 콘솔로 감지해 원인을 잡습니다.

### Q9. 컨테이너 이미지는 어떻게 관리·배포하나요?
> 🎯 출제확률 **62%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.86

**답변:** 이미지는 **GitHub Container Registry(ghcr.io)** 에 빌드해 올리고(`ghcr.io/.../ada-api:latest` 등), VPS는 그걸 pull 해서 띄웁니다. 빌드는 **GitHub Actions(CI)** 가 자동 수행합니다. 코드(파이썬)는 일부 **라이브 마운트**(`../api:/app/api` 등)해서, 작은 수정은 이미지 재빌드 없이 반영되게 했습니다.

### Q10. 코드를 한 줄 고치면 어떻게 반영되나요? 매번 재빌드하나요?
> 🎯 출제확률 **66%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.98

**답변:** **경우에 따라 다릅니다.** ① 프론트엔드(Streamlit)는 소스를 **라이브 마운트 + 파일 와처(poll)** 해서 **새로고침(F5) 한 번**이면 반영됩니다(재빌드 X). ② API·워커의 파이썬 코드도 마운트돼 있어 **컨테이너 재생성**(`up -d --force-recreate`)이면 반영됩니다. ③ **의존성(requirements)·Dockerfile**이 바뀌면 그때만 **이미지 재빌드**가 필요합니다. 즉 "코드만 = 재시작/새로고침, 패키지 = 재빌드"로 나눴습니다.

### Q11. 컨테이너 간 통신은 어떻게 하나요?
> 🎯 출제확률 **52%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.56

**답변:** 모든 컨테이너를 **하나의 도커 브리지 네트워크(`ada-net`)** 에 묶어, **서비스 이름으로 서로 호출**합니다(예: api가 `postgres:5432`, `mlflow:5000`으로 접속). 외부 노출이 필요한 포트만 `127.0.0.1:`에 바인딩해 **로컬호스트로 제한**하고, 실제 외부 공개는 **nginx(80/443)** 만 담당합니다. 호스트(VPS)의 Ollama 같은 서비스는 `host.docker.internal`로 접근합니다.

### Q12. 워커가 호스트의 Ollama를 못 찾는 문제가 있었다는데?
> 🎯 출제확률 **45%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 1.8

**답변:** 실제로 겪었습니다. **Linux 컨테이너는 `host.docker.internal`이 기본으로 DNS 해석이 안 됩니다**(Mac/Win은 자동). api 서비스에는 `extra_hosts: host.docker.internal:host-gateway` 매핑이 있었는데 **워커 서비스엔 빠져** 있어, 워커 안 에이전트의 Ollama 호출이 전부 실패했습니다(`gaierror`). **compose의 워커 5종에 `extra_hosts`를 추가**해 해결했고, 임시로는 `docker-compose.override.yml`로 보강 후 base에 반영해 영구화했습니다. (→ 13번 장애대응에서 상세)

## 3. 데이터 계층 (PostgreSQL · Redis · MinIO · MLflow)

### Q13. 데이터 저장소 4종의 역할을 각각 설명해 주세요.
> 🎯 출제확률 **85%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 3.4

**답변:** 용도가 다른 4종을 씁니다.

| 저장소 | 역할 | 비유 |
|---|---|---|
| **PostgreSQL + pgvector** | 관계형 데이터(작업·사용자·KB) + **벡터 검색**(임베딩) | 본부 서류 캐비닛 |
| **Redis** | 고속 캐시·세션·Celery 큐·회로차단 상태 공유 | 책상 위 메모지 |
| **MinIO (S3 호환)** | 큰 파일(산출물·모델·데이터셋) 객체 저장 | 대형 창고 |
| **MLflow** | 학습 실험·모델 버전 추적 | 실험 노트 |

**핵심:** "정형 데이터·벡터는 Postgres, 빠른 휘발성은 Redis, 큰 파일은 MinIO, 학습 기록은 MLflow."

### Q14. 왜 벡터 DB를 따로 안 쓰고 pgvector를 썼나요?
> 🎯 출제확률 **58%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.32

**답변:** **운영 단순화** 때문입니다. 전용 벡터 DB(Pinecone·Weaviate 등)를 추가하면 서버가 하나 더 늘고 비용·관리가 커집니다. **PostgreSQL에 pgvector 확장**을 얹으면 **기존 DB 하나로 정형 데이터 + 의미 검색**(`<=>` 코사인 거리)을 모두 처리합니다. KB·임베딩 규모가 우리 수준에선 pgvector로 충분히 빠르고, 트랜잭션·백업도 DB 하나로 통합 관리됩니다.

### Q15. 데이터 일관성·트랜잭션은 어떻게 보장하나요?
> 🎯 출제확률 **50%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.5

**답변:** 핵심 데이터는 **PostgreSQL 트랜잭션**으로 보장합니다. 분석 워커가 DB를 쓸 때 **성공 시 commit, 예외 시 rollback**을 자동 처리하고, "분석 성공 > DB 기록"이라 **DB 기록 실패가 분석을 깨뜨리지 않게**(best-effort) 격리했습니다. 스키마 변경은 반드시 **Alembic 마이그레이션**으로 버전 관리합니다.

### Q16. DB 스키마가 바뀌면 어떻게 배포하나요?
> 🎯 출제확률 **48%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.44

**답변:** **Alembic 마이그레이션**으로 합니다. 스키마 변경은 코드가 아니라 마이그레이션 파일(`migrations/versions/*`)로 작성하고, 배포 시 `alembic upgrade head`로 적용합니다. 되돌릴 땐 `downgrade`. 이렇게 해야 **여러 환경(로컬·VPS)의 DB 구조가 동일하게** 유지됩니다.

### Q17. MinIO는 왜 썼나요? 그냥 디스크에 저장하면 안 되나요?
> 🎯 출제확률 **45%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.35

**답변:** **확장성·호환성** 때문입니다. PPT·PDF·모델 같은 큰 파일을 DB에 넣으면 DB가 무거워지고, 로컬 디스크에 흩어두면 관리·접근이 어렵습니다. MinIO는 **S3 호환 객체 스토리지**라, 코드가 표준 S3 API로 접근하고, 나중에 진짜 AWS S3로 옮겨도 코드 변경이 거의 없습니다. MLflow의 아티팩트 저장소로도 MinIO를 씁니다.

### Q18. 로컬과 운영(VPS)의 DB는 같은 건가요?
> 🎯 출제확률 **42%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.68

**답변:** **완전히 별개입니다.** 로컬 개발 PC의 PostgreSQL과 VPS의 PostgreSQL은 다른 인스턴스라, 데이터·설정이 공유되지 않습니다. 실제로 "운영 콘솔이 로컬은 뜨는데 도메인은 안 뜨는" 문제가 있었는데, **권한(role)을 로컬 DB에만 바꾸고 VPS DB엔 안 바꿔서** 생긴 일이었습니다. 그래서 **환경별로 DB를 따로 관리**하는 점을 항상 의식합니다.

## 4. 네트워크 · SSH 터널 · NAT 우회

### Q19. NAT 뒤에 있는 로컬 서버에 VPS가 어떻게 접속하나요?
> 🎯 출제확률 **88%** · 중요도 ★★★★★ · 우선순위 **S** · 준비점수 4.4

**답변:** **SSH 역터널(reverse tunnel)** 로 NAT를 우회합니다. 로컬 서버는 사설 IP + NAT 뒤라 **밖에서 직접 못 들어갑니다.** 하지만 **안→밖(아웃바운드)** 은 됩니다. 그래서 **로컬 서버가 먼저 VPS로 SSH 연결을 걸고**, `ssh -R`(역방향 포워딩)로 **VPS의 포트를 로컬 서비스에 연결**합니다. 그러면 VPS가 자기 `localhost:11434`에 접속하는 것만으로 로컬 GPU의 Ollama에 닿습니다. 이미 열린 아웃바운드 통로를 되돌려 쓰는 원리라 NAT를 뚫지 않고도 통신됩니다.

**한 문장:** "로컬이 밖으로 전화를 걸어 뒷문을 열어주고, VPS는 그 선으로 로컬 Ollama를 씁니다."

### Q20. 그 터널이 끊기면요? 안정성은?
> 🎯 출제확률 **60%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.4

**답변:** **autossh**로 해결합니다. 그냥 ssh는 네트워크가 잠깐 끊기거나 재부팅되면 터널이 죽고 안 돌아옵니다. autossh는 ssh를 감싸 **연결 상태를 감시하다가 끊기면 자동 재연결**합니다. 보통 **systemd 서비스로 등록**해 부팅 시 자동 시작 + 24시간 유지합니다. 그래서 다이어그램에 "autossh"라고 명시한 겁니다.

### Q21. 터널로 어떤 트래픽이 오가나요?
> 🎯 출제확률 **50%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.5

**답변:** **양방향**입니다. ① **VPS → 로컬**: 역터널(`-R`)로 VPS가 로컬 Ollama(11434)를 호출. ② **로컬 → VPS**: 정방향(`-L`)으로 로컬 GPU 학습 워커가 VPS의 PostgreSQL·Redis·MinIO·MLflow에 접속해 학습 데이터를 읽고 결과를 저장. 모두 **SSH로 암호화**되어 흐릅니다.

### Q22. 그냥 포트포워딩하거나 VPN을 쓰면 안 되나요?
> 🎯 출제확률 **40%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.2

**답변:** **권한·보안·비용** 때문에 SSH 터널이 최적이었습니다. 학원 공유기의 포트포워딩은 관리자 권한이 필요하고 보안 노출이 큽니다. VPN은 별도 인프라·비용이 듭니다. SSH 터널은 **추가 장비·비용 0**, **이미 있는 SSH로 암호화**, **로컬이 먼저 거는 방식이라 인바운드 포트 개방 불필요**라 가장 가볍고 안전합니다.

### Q23. nginx는 어떤 역할을 하나요?
> 🎯 출제확률 **55%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.65

**답변:** **리버스 프록시 + HTTPS 종단**입니다. 외부의 80/443 요청을 받아 내부 컨테이너(`/api`→FastAPI, 그 외→Streamlit)로 전달합니다. SSL 인증서(Let's Encrypt)를 nginx가 처리해 **HTTPS 보안**을 제공합니다. `/api` 경로를 떼고 백엔드에 넘기는 규칙 때문에, 구글 OAuth 콜백 URL도 운영에선 `/api`를 포함해야 합니다.

### Q24. 포트는 어떻게 통제하나요? 외부에 다 열려 있나요?
> 🎯 출제확률 **58%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.74

**답변:** **최소 노출 원칙**입니다. 외부로 진짜 열린 건 **nginx(80/443)** 뿐입니다. 나머지(PostgreSQL 5432, Redis 6379, MinIO, MLflow 등)는 **`127.0.0.1`(로컬호스트)에만 바인딩**해 외부에서 직접 접근 불가합니다. 호스트 방화벽(**UFW**)으로도 불필요한 포트를 막습니다. Ollama(11434)는 도커 내부망·터널로만 접근합니다.

## 5. 보안 (인증·시크릿·암호화·방화벽)

### Q25. 시크릿(.env)을 어떻게 안전하게 관리하나요?
> 🎯 출제확률 **85%** · 중요도 ★★★★★ · 우선순위 **S** · 준비점수 4.3

**답변:** **3겹**으로 관리합니다. ① 평문 `.env`는 **git에 절대 안 올리고**(`.gitignore`), 권한을 **`600`(소유자만 읽기)** 으로 잠급니다. ② 백업·버전관리는 **SOPS + age로 암호화한 `.env.sops`** 로 합니다 — 암호문이라 git에 올려도 안전하고, age 개인키가 있어야만 복호화됩니다(개인키는 서버·관리자에만 보관). ③ 더 민감한 시크릿은 **Vault**(sec 프로파일)로 관리하는 경로도 마련했습니다. "**평문은 잠그고, 백업은 암호화하고, 키는 분리**"가 원칙입니다.

**암기:** ".env는 600·gitignore, .env.sops는 SOPS/age 암호화 백업, 키는 분리 보관."

### Q26. 인증·인가는 어떻게 구현했나요?
> 🎯 출제확률 **78%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 3.1

**답변:** **JWT(RS256) + RBAC**입니다. 로그인하면 **RS256(비대칭 서명) JWT 토큰**을 발급하고, 모든 API가 이 토큰으로 사용자·역할을 검증합니다. 권한은 **RBAC**(역할 기반 접근 제어)로, 엔드포인트마다 `require_perm(...)`을 걸어 **역할에 맞는 사람만** 접근합니다(예: 운영 콘솔은 `admin` 역할만). 구글 OAuth 로그인도 지원하며, 콜백에서 토큰을 발급합니다.

### Q27. RS256을 쓴 이유는? HS256과 차이는?
> 🎯 출제확률 **48%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.44

**답변:** **비대칭 키**라 더 안전하기 때문입니다. HS256(대칭)은 검증하는 모든 곳이 같은 비밀키를 공유해야 해서, 한 곳만 유출돼도 위조가 가능합니다. **RS256은 개인키(서명)와 공개키(검증)가 분리**되어, 토큰 발급은 개인키를 가진 인증 서버만, 검증은 공개키로 누구나 할 수 있습니다. 분산 환경에서 키 유출 위험을 줄이는 정석입니다(룰 R-707).

### Q28. PII(개인정보)는 어떻게 보호하나요?
> 🎯 출제확률 **68%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.7

**답변:** **마스킹 + 익명화**로 다층 보호합니다. ① **로그 PII 마스킹**: 모든 로그는 자동 마스킹 처리되어 개인정보가 안 찍힙니다(룰 R-103). ② **LLM 익명화→재부착**: 데이터를 LLM에 보내기 전 개인정보를 토큰으로 익명화하고, 답을 받은 뒤 원래 값으로 복원합니다 → **LLM은 진짜 개인정보를 절대 못 봅니다.** ③ 에러 원문은 **AES-GCM으로 암호화** 저장합니다.

### Q29. 프롬프트 인젝션 같은 LLM 공격은 어떻게 막나요?
> 🎯 출제확률 **45%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.8

**답변:** **입력 가드 + 출력 스키마 강제**입니다. ① 사용자·데이터 입력은 **LLM Guard**로 악성·유해 입력을 사전 차단합니다(R-1002). ② 데이터·문서에 숨겨진 지시문이 LLM을 탈취하는 **간접 인젝션**도 가드로 막습니다(R-708). ③ LLM 출력은 **Guardrails AI 스키마**로 정해진 형식만 통과시킵니다(R-1005). 즉 들어오는 것과 나가는 것을 모두 검증합니다.

### Q30. 방화벽·네트워크 보안은?
> 🎯 출제확률 **52%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.56

**답변:** **UFW 방화벽 + 최소 포트 노출**입니다. 외부 공개는 80/443(nginx)뿐, DB·캐시·스토리지는 모두 로컬호스트 바인딩. 서버 간 통신은 SSH 터널로 암호화. SSH 자체도 키 기반 인증을 씁니다. "**열 필요 없는 건 다 막는다**"가 원칙입니다.

### Q31. 시크릿이 유출되면 어떻게 대응하나요?
> 🎯 출제확률 **40%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.6

**답변:** **로테이션(교체) 런북**이 있습니다. 키가 유출되면 ① 해당 시크릿(API 키·비밀번호)을 **즉시 재발급**하고 ② `.env` 갱신 후 **컨테이너 재생성**으로 반영, ③ `.env.sops` 재암호화로 백업 동기화, ④ 감사 로그로 영향 범위를 확인합니다. SOPS 덕에 암호화 백업은 유출돼도 age 키 없이는 못 풉니다.

### Q32. 운영 콘솔 접근은 누가 가능한가요?
> 🎯 출제확률 **42%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.26

**답변:** **DB의 `users.role`이 `admin`인 사람만** 운영 콘솔 버튼이 보이고 진입됩니다. 구글 OAuth 신규 로그인은 기본 `analyst`로 생성되므로, 관리자는 **대상 환경 DB에서 role을 명시적으로 admin으로 승격**해야 합니다(코드에 자동 화이트리스트 없음). 환경별 DB가 별개라 VPS DB에서 직접 승격합니다.

## 6. LLM 인프라 (3-tier · Ollama · 회로차단)

### Q33. 3-tier LLM 구조로 비용을 어떻게 절감했나요?
> 🎯 출제확률 **90%** · 중요도 ★★★★★ · 우선순위 **S** · 준비점수 4.5

**답변:** **싼 것부터 순서대로** 쓰는 폴백 구조입니다. 질문/작업이 오면 ① **1순위 팀 KB(무료)** — 과거에 답한 적 있으면 즉시 재사용, ② **2순위 로컬 Ollama(무료)** — 학원 GPU의 qwen2.5:7b, ③ **3순위 클라우드 Claude(유료)** — 가장 똑똑하지만 비싸서 **최후에만**. 반복 질문이나 일반 분석은 무료 단계에서 끝나고, 정말 어려운 것만 유료를 부르므로 **클라우드 API 비용이 크게 절감**됩니다. 게다가 Claude의 좋은 답은 자동으로 KB에 학습돼, 다음엔 무료로 재사용됩니다.

**암기:** "팀 KB(무료) → Ollama(무료) → Claude(유료) 순. 비싼 건 최후에만."

### Q34. 분석에 무료 로컬 LLM을 쓰면 품질이 떨어지지 않나요?
> 🎯 출제확률 **58%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.32

**답변:** **작업 난이도에 따라 분리**해 품질을 지킵니다. 단순·반복 작업(윤색, 분류, 방향 제안 등)은 Ollama로 충분하고, **복잡한 추론·핵심 인사이트**는 Claude를 씁니다. 기본값은 `USE_OLLAMA_FOR_ANALYSIS=true`로 분석 LLM을 Ollama로 두되, 필요 시 클라우드로 올립니다. 즉 "**쉬운 건 무료, 어려운 건 유료**"로 비용과 품질의 균형을 맞춥니다.

### Q35. 외부 LLM(Claude·Ollama)이 장애가 나면 시스템이 멈추나요?
> 🎯 출제확률 **75%** · 중요도 ★★★★★ · 우선순위 **S** · 준비점수 3.75

**답변:** 아니요, **회로차단기(Circuit Breaker)** 로 버팁니다. Ollama·Claude API 등 외부 의존성이 죽으면, 무한 재호출로 전체가 멈추는 걸 막습니다. **연속 실패가 임계치를 넘으면 회로를 OPEN으로 끊고**(빠른 폴백), 일정 시간 뒤 HALF_OPEN으로 살짝 떠보고, 성공하면 다시 CLOSED로 복구합니다. **Redis로 차단 상태를 공유**해 모든 워커가 같은 판단을 합니다. 한 LLM이 죽어도 다음 tier로 폴백하니 서비스는 계속됩니다(R-709).

**비유:** "두꺼비집 — 한 회로에 문제 생기면 그것만 끊고 집 전체는 살린다."

### Q36. Ollama는 어디서 도나요? VPS인가요 로컬인가요?
> 🎯 출제확률 **55%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.2

**답변:** **학원 GPU 로컬 서버**에서 돕니다(GTX 1060). VPS는 GPU가 없어 직접 못 돌리고, **SSH 역터널로 로컬 Ollama에 연결**해 씁니다. 그래서 VPS의 워커·API가 `host.docker.internal:11434`로 Ollama를 부르면 실제로는 로컬 GPU가 응답합니다. 모델은 `qwen2.5:7b`(분석)와 `qwen2.5-coder:7b`(코드/에러수정)를 씁니다.

### Q37. 같은 오류가 반복되면 매번 LLM 비용이 드나요?
> 🎯 출제확률 **48%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.92

**답변:** 아니요, **자가치유(self-healing) 학습**으로 막습니다. 오류가 나면 4단계로 고칩니다 — ① ErrorKB 해시 매칭(무료) → ② 과거 수정 사례 의미 검색(무료) → ③ Ollama 코더 모델(무료) → ④ Claude(유료, 최후). 새로 만든 패치는 **샌드박스 검증 후 KB에 저장**되어, **같은 오류의 두 번째 발생부턴 무료·즉시** 해결됩니다. 즉 한 번 고친 오류는 다시는 비용이 안 듭니다.

### Q38. KB(지식베이스)가 잘못된 지식을 학습하면요?
> 🎯 출제확률 **40%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.2

**답변:** **신뢰도 생애주기 + 품질 게이트**로 도태시킵니다. 모든 지식은 신뢰도(confidence)를 갖고, 쓸 때 맞으면 오르고(+0.05) 틀리면 빠르게 내립니다(−0.10). **60일 안 쓰면 감쇠, 0.20 밑이면 자동 폐기**(검색 제외). 저장 시에도 "죄송합니다/모르겠습니다" 같은 거부 답변은 품질 게이트가 걸러냅니다. "**신뢰는 천천히, 잃는 건 빠르게**"로 나쁜 지식이 못 살아남습니다.

### Q39. main 브랜치를 어떻게 보호하나요?

### Q51. 왜 Push가 아니라 Pull 방식인가요?
> 🎯 출제확률 **45%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.8

### Q52. VPS가 완전히 죽으면 복구 절차는?

### Q56. 사용자가 늘면(트래픽 증가) 어떻게 확장하나요?
> 🎯 출제확률 **60%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.4

**답변:** **수평·수직 확장 경로**가 있습니다. ① 분석 작업은 **Celery 워커를 늘려**(컨테이너 추가) 처리량을 키웁니다. ② 웹/DB는 VPS 사양을 올리거나(수직), 부하가 커지면 관리형 DB·로드밸런서로 옮길 수 있습니다(MinIO→S3, pgvector→전용 벡터 DB). ③ LLM은 무료 tier(KB·Ollama)가 부하를 흡수해 유료 비용 급증을 막습니다. 컨테이너·S3 호환 설계라 **클라우드 이전이 쉽습니다.**

### Q57. 가장 어려웠던 기술적 의사결정은 무엇이었나요?
> 🎯 출제확률 **55%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.2

**답변:** **"GPU를 어떻게 쓸 것인가"** 였습니다. 클라우드 GPU는 너무 비싸고, 보유 GPU는 NAT 뒤라 외부에서 못 씁니다. 이걸 **SSH 역터널(autossh)로 NAT를 우회**해 VPS가 로컬 GPU Ollama를 쓰게 한 결정이 핵심이었습니다. 덕분에 **추가 비용 0으로 GPU 추론**을 확보했고, 3-tier LLM의 무료 2순위가 완성됐습니다.

### Q58. 이 아키텍처의 약점·한계는 무엇인가요? (솔직하게)
> 🎯 출제확률 **58%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.32

**답변:** 솔직히 ① **단일 VPS라 그 서버가 죽으면 사이트가 내려갑니다**(완전 이중화는 아님 — 대신 백업으로 빠른 복구). ② **로컬 서버가 학원 네트워크·전원에 의존**해, 거기가 끊기면 GPU·Ollama가 멈춥니다(회로차단으로 클라우드 폴백). ③ GTX 1060은 큰 모델엔 한계가 있어 7B급으로 제한됩니다. 운영 규모가 커지면 **이중화·관리형 전환**이 다음 과제입니다. 다만 **컨테이너·S3 호환·git/SOPS 백업**으로 그 전환이 쉽도록 설계해 뒀습니다.

### Q59. 보안과 비용 중 무엇을 우선했나요?
> 🎯 출제확률 **38%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.14

**답변:** **둘 다 포기하지 않는 선**을 찾았습니다. 비용은 보유 자원·무료 대체로 낮추되, 보안은 **타협하지 않았습니다** — 시크릿 암호화(SOPS), JWT RS256, PII 마스킹, 최소 포트 노출, Pull 백업. "싸게 만들되 안전은 정석대로"가 원칙이었습니다.

## 11. 실제 장애·이슈 대응 사례 (가장 임팩트 큰 카테고리)

> 발표에서 **"직접 겪고 고친 사례"** 는 신뢰도를 크게 높입니다. 아래는 이번 운영에서 실제로 해결한 사례입니다.

### Q60. 실제로 겪은 장애와 해결 과정을 하나 말해 주세요.
> 🎯 출제확률 **80%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 3.2

**답변(대표 사례 — 워커 Ollama 연결 실패):** 어느 날 **분석 워커가 Ollama를 호출하면 전부 실패**했습니다. 에러는 `gaierror: Name or service not known` — 연결 거부가 아니라 **`host.docker.internal` 이름 자체가 DNS로 안 풀리는** 문제였습니다. 원인은 **Linux 컨테이너는 이 이름을 기본 해석 못 하는데**, api 서비스엔 `extra_hosts: host.docker.internal:host-gateway` 매핑이 있고 **워커 서비스엔 빠져** 있었던 것. ① 우선 `ada-api`로 테스트해 호스트 Ollama 자체는 200(정상)임을 확인하고, ② 워커가 문제임을 특정한 뒤, ③ `docker-compose.override.yml`로 워커 5종에 `extra_hosts`를 임시 보강해 즉시 복구(worker→Ollama 200 확인), ④ 마지막으로 **base compose에 영구 반영(PR 머지)** 해 재배포에도 안 풀리게 했습니다. **"증상→원인 격리(api는 되는데 워커는 안 됨)→임시 복구→영구화"** 순서로 처리한 게 핵심입니다.

### Q61. "로컬은 되는데 운영(도메인)은 안 되는" 문제를 겪은 적 있나요?
> 🎯 출제확률 **52%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.08

**답변:** 네. **운영 콘솔이 로컬에선 뜨는데 도메인에선 안 뜨는** 문제였습니다. 원인은 **로컬 DB와 VPS DB가 별개**인데, 관리자 권한(role=admin)을 **로컬 DB에만 바꾸고 VPS DB엔 안 바꿔서**였습니다. 운영 콘솔 버튼은 그 환경 DB의 `users.role='admin'`일 때만 보이는데, VPS DB는 여전히 `analyst`였던 것. **VPS DB에서 직접 role을 admin으로 승격**하고 재로그인(토큰 갱신)하니 해결됐습니다. 교훈은 "**환경별 DB는 별개다 — 운영은 운영 DB를 봐야 한다**"입니다.

### Q62. 운영 중 "하면 안 되는 작업"이 막힌 경험이 있나요?
> 🎯 출제확률 **40%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.2

**답변:** 네, **main 직접 push가 거부**됐습니다. 인프라 수정을 빨리 반영하려고 main에 바로 push했더니 `GH006: Protected branch ... Changes must be made through a pull request` + 상태체크 2개 필수라는 거부가 떴습니다. 이건 **가드레일이 의도대로 작동**한 것이라, 우회하지 않고 **브랜치 분리 → push → PR → 리뷰·CI → 머지** 정석 경로로 반영했습니다. 안전장치가 사람의 실수를 막아준 좋은 사례입니다.

### Q63. 시크릿 관리를 개선한 사례가 있나요?
> 🎯 출제확률 **42%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.68

**답변:** 네. 원래 평문 `.env`만 서버에 있었는데, **SOPS + age 암호화**를 도입해 `.env.sops`(암호문)를 git으로 버전관리하게 바꿨습니다. 평문 `.env`는 `600` 권한 + gitignore로 잠그고, 암호화 백업은 git에 올려도 안전합니다. 추가로 `.env`를 **대기업 정석대로 섹션화**(환경 식별/인프라/시크릿/토글)하되, **값은 한 글자도 안 바꾸고 순서·주석만** 정리하는 안전 절차(백업→임시파일 생성→값 동일 검증→교체)를 만들었습니다.

### Q64. 임시 해결과 영구 해결을 어떻게 구분하나요?
> 🎯 출제확률 **38%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.14

**답변:** **"지금 복구"와 "다시 안 터지게"를 분리**합니다. 장애가 나면 우선 **override 파일·수동 조치로 즉시 복구**(서비스 우선)하고, 그 다음 **근본 원인을 base 설정·코드에 반영해 PR로 영구화**합니다. 워커 Ollama 사례가 그랬습니다 — override로 급한 불을 끄고, base compose 커밋으로 영구화했습니다. 임시 조치는 git 추적이 안 되니 **반드시 영구화로 마무리**하는 걸 원칙으로 합니다.

### Q65. 가장 자랑스러운 인프라 성과 한 가지는?
> 🎯 출제확률 **50%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.0

**답변:** **월 2~3만원으로 GPU·LLM·자가치유까지 갖춘 운영 시스템을 만든 것**입니다. 보유 GPU를 SSH 터널로 끌어와 무료 LLM 추론을 확보했고, 3-tier로 유료 비용을 최소화했으며, 회로차단·자가치유·자동 백업으로 **저비용이지만 죽지 않는** 인프라를 구축했습니다. "**돈을 적게 쓰면서도 정석 안정성을 지켰다**"는 점이 가장 자랑스럽습니다.

## 12. 기술 선택 근거 & 비교 (왜 X 대신 Y)

> "왜 그 기술을 골랐나"는 단골 질문입니다. **대안과 비교**하며 이유를 말하면 신뢰도가 올라갑니다.

### Q66. 왜 프론트를 Streamlit으로 했나요? React 같은 정식 프론트가 아니라?
> 출제확률 **55%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.65

**답변:** **개발 속도와 목적** 때문입니다. 우리 화면은 화려한 UI가 아니라 **데이터·분석 결과를 빠르게 보여주는 대시보드**가 핵심입니다. React는 강력하지만 별도 빌드·상태관리·API 연동에 시간이 많이 듭니다. Streamlit은 **파이썬만으로 데이터 화면을 즉시** 만들 수 있어, 분석 결과·차트·게이트(HITL) 화면을 빠르게 구현했습니다. 5주 일정에서 프론트에 시간을 덜 쓰고 분석 엔진에 집중하기 위한 합리적 선택이었습니다. 라이브 마운트로 **새로고침만으로 반영**되는 것도 운영에 유리했습니다.

### Q67. 왜 API 서버로 FastAPI를 골랐나요?
> 출제확률 **48%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.44

**답변:** **비동기 + 자동 문서화 + 타입 검증**이 강점이라서입니다. FastAPI는 `async`로 LLM·DB I/O를 효율적으로 처리하고, Pydantic으로 요청·응답을 **자동 검증**하며, Swagger 문서를 자동 생성합니다. 분석은 외부 LLM·DB를 많이 기다리는 I/O 작업이라 비동기가 특히 유리했습니다.

### Q68. 왜 Celery로 작업을 분리했나요? API에서 바로 돌리면 안 되나요?
> 출제확률 **58%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.32

**답변:** **무거운 분석은 오래 걸려서**입니다. 분석·학습은 수십 초~수 분이 걸리는데, 이걸 API 요청 안에서 처리하면 사용자가 끝까지 기다리고 타임아웃·서버 점유가 생깁니다. **Celery 워커**로 작업을 큐에 넣어 **백그라운드 비동기 처리**하면, API는 즉시 응답하고 무거운 일은 워커가 따로 돕니다. 큐도 `pipeline`·`harness`·`training`·`output`으로 나눠, **GPU 학습이 일반 분석을 막지 않도록**(bulkhead) 격리했습니다.

### Q69. 왜 Kubernetes가 아니라 docker-compose인가요?
> 출제확률 **52%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.08

**답변:** **규모에 맞는 선택**입니다. Kubernetes는 수십~수백 노드를 다루는 대규모용이라, **서버 2대** 규모엔 과합니다(학습·운영 부담만 큼). docker-compose는 **선언적 정의 + 프로파일 + 헬스체크·자동재시작**으로 우리 규모에 필요한 오케스트레이션을 충분히 제공합니다. 나중에 커지면 compose 정의를 기반으로 k8s로 옮기는 경로도 열려 있습니다. "**지금 규모에 가장 단순하고 충분한 도구**"를 고른 것입니다.

### Q70. 왜 LangGraph를 썼나요? 그냥 함수 호출로 연결하면 안 되나요?
> 출제확률 **45%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.35

**답변:** **흐름의 명시성·복원·HITL** 때문입니다. 28개 에이전트를 함수로 줄줄이 호출하면 분기·재시도·중단점이 코드에 흩어져 추적이 어렵습니다. LangGraph는 에이전트를 **노드, 흐름을 그래프**로 선언해 한눈에 보이고, **상태(PipelineState)를 체크포인트로 저장**해 중단·재개가 됩니다. 특히 **게이트(HITL)에서 사람 확인을 위해 멈췄다 재개**하는 기능이 그래프 모델과 잘 맞습니다.

### Q71. 왜 로컬 모델로 qwen2.5를 골랐나요?
> 출제확률 **42%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.26

**답변:** **성능 대비 크기·한국어** 균형입니다. GTX 1060(6GB급)에서 돌릴 수 있는 **7B 크기**이면서, 한국어·코드 성능이 동급에서 우수합니다. 분석 윤색·방향 제안엔 `qwen2.5:7b`, 에러 수정 diff 생성엔 코드 특화 `qwen2.5-coder:7b`를 씁니다. 더 큰 모델은 1060에 안 올라가고, 더 작은 모델은 품질이 떨어져 이 크기가 최적이었습니다.

### Q72. 왜 시크릿을 Vault와 SOPS 둘 다 쓰나요?
> 출제확률 **38%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.14

**답변:** **용도가 다릅니다.** SOPS는 **`.env` 파일 자체를 암호화해 git으로 백업·버전관리**하는 데 적합합니다(정적 시크릿의 안전한 보관·복구). Vault는 **동적 시크릿·세밀한 접근제어·감사 로그**가 필요한 런타임 시크릿 관리에 강합니다. 현재 규모에선 SOPS로 충분히 운영하되, 더 엄격한 관리가 필요할 때 Vault로 승급하는 경로를 마련해 둔 것입니다.

### Q73. MLflow와 LangFuse를 둘 다 쓰는 이유는?
> 출제확률 **40%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.2

**답변:** **추적 대상이 다릅니다.** MLflow는 **모델 학습**(파라미터·지표·아티팩트·모델 버전)을 추적하고, LangFuse는 **LLM 호출**(프롬프트·토큰·비용·지연)을 추적합니다. 즉 "**모델은 MLflow, LLM은 LangFuse**"로 역할이 갈립니다. 둘을 합치면 학습부터 LLM 비용까지 전 과정이 관측됩니다.

## 13. 시나리오·압박 질문 (심화 대비)

> 면접식 "만약에" 질문 대비. 정답보다 **"어떻게 생각하고 대응하는가"** 를 보여주는 게 핵심입니다.

### Q74. 트래픽이 갑자기 10배가 되면 가장 먼저 어디가 터지나요?
> 출제확률 **52%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.08

**답변:** 단계별로 보면 ① 먼저 **분석 워커(Celery)** 가 큐 적체로 느려집니다 → **워커 컨테이너를 늘려** 대응. ② 다음으로 **로컬 GPU(Ollama)** 가 병목(1060 한 대) → **무료 KB 캐시 적중률**로 흡수하고, 안 되면 클라우드 폴백. ③ **단일 VPS의 CPU·메모리** → 사양 업 또는 웹/DB 분리. 즉 **병목 순서를 알고 있고, 각 지점마다 대응책(워커 증설·KB 캐시·사양 업)** 이 있다는 게 핵심 답변입니다.

### Q75. PostgreSQL 디스크가 꽉 차면 어떻게 되나요?
> 출제확률 **45%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.8

**답변:** DB 쓰기가 실패하기 시작합니다. 대응은 ① **운영 콘솔의 DB 용량 모니터링**으로 사전 감지(임계 경고), ② 큰 파일은 애초에 **MinIO(객체 스토리지)** 로 빼서 DB를 가볍게 유지, ③ 오래된 로그·KB는 **감쇠·폐기 정책**으로 정리, ④ 그래도 부족하면 **볼륨 확장**. 설계 단계에서 "큰 건 DB에 안 넣는다"로 디스크 압박을 줄였습니다.

### Q76. Ollama 응답이 너무 느려지면 사용자는 무한 대기하나요?
> 출제확률 **48%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.92

**답변:** 아니요. ① **타임아웃**을 걸어 일정 시간 넘으면 끊고, ② **회로차단기**가 연속 실패·지연을 감지해 OPEN으로 전환하면 **다음 tier(클라우드)로 폴백**합니다. ③ 무거운 작업은 애초에 **백그라운드(Celery)** 라 사용자 화면이 멈추지 않습니다. "느린 의존성이 사용자 경험을 잡아먹지 않게" 타임아웃+회로차단+비동기 3중으로 막습니다.

### Q77. 학원 인터넷·전원이 끊기면 어떤 일이 벌어지나요?
> 출제확률 **50%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.0

**답변:** 로컬 서버(GPU·Ollama·백업)가 멈춥니다. 영향과 대응 — ① SSH 터널이 끊기면 **autossh가 복구 시도**, ② Ollama 불가 시 **회로차단 → 클라우드 Claude로 폴백**(분석은 계속), ③ 그 시간 백업은 일시 중단되지만 **다음 스케줄(03/12/18시)에 재개**, ④ 웹·DB는 VPS에 있어 **사이트 자체는 정상**. 즉 로컬 의존 기능만 일시 저하되고 핵심 서비스는 유지됩니다.

### Q78. 클라우드 LLM 비용이 갑자기 폭증하면 어떻게 막나요?
> 출제확률 **55%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.2

**답변:** **예산 가드 + 3-tier 구조**로 막습니다. ① **일일 예산 한도**(`MAX_DAILY_LLM_USD`)를 넘으면 유료 호출을 차단·경고, ② 애초에 **무료 KB·Ollama가 대부분을 처리**해 유료 호출 비중이 낮고, ③ **LangFuse로 실시간 비용 추적**해 이상 급증을 즉시 감지, ④ 반복 질문은 **KB 학습으로 두 번째부턴 무료**. "비용이 새는 구조를 설계 단계에서 차단"한 것입니다.

### Q79. 보안 감사(audit)가 들어오면 무엇을 보여줄 수 있나요?
> 출제확률 **40%** · 중요도 ★★★ · 우선순위 **B** · 준비점수 1.2

**답변:** ① **감사 로그**(`security_audit_log`) — 로그인·권한 변경·PII 마스킹 이력, ② **시크릿 관리 증빙**(.env 600 권한·SOPS 암호화·키 분리), ③ **접근제어**(JWT RS256·RBAC 매트릭스), ④ **PII 보호**(마스킹·익명화·AES-GCM 암호화), ⑤ **네트워크**(최소 포트·UFW·SSH 암호화)를 제시할 수 있습니다. "누가·언제·무엇을 했는지" 추적 가능한 구조라 감사 대응이 됩니다.

### Q80. 누군가 실수로 운영 DB를 통째로 지우면요?
> 출제확률 **42%** · 중요도 ★★★★★ · 우선순위 **A** · 준비점수 2.1

**답변:** **백업으로 복구**합니다. 로컬 백업 서버에 **하루 3회 pg_dump 사본(14일 보존)** 이 있으니, 최악의 경우에도 **최대 8시간 전 상태**로 되돌립니다. 복구는 최신 dump를 PostgreSQL에 restore → 데이터셋은 MinIO에서 → `alembic`으로 스키마 확인 순. 또 운영 DB 삭제 같은 위험 작업은 **admin 권한 + 명시적 확인**이 필요하도록 제한했습니다. "지워져도 복구되고, 애초에 아무나 못 지운다"가 답입니다.

### Q81. 새 팀원이 와서 개발 환경을 세팅하려면 얼마나 걸리나요?
> 출제확률 **38%** · 중요도 ★★★ · 우선순위 **C** · 준비점수 1.14

**답변:** **거의 자동화**돼 있어 짧습니다. git clone → `.env` 설정(SOPS 복호화) → `docker compose up -d` 면 전체 스택이 뜹니다. pre-commit 훅·CODEOWNERS가 자동 설치돼 영역 가드가 바로 작동하고, 시드 스크립트로 초기 데이터가 채워집니다. "컨테이너 + 선언적 설정"이라 **사람마다 환경이 달라 생기는 문제("내 PC에선 되는데")** 가 거의 없습니다.

### Q82. SSH 터널 키가 유출되면 어떻게 되나요?
> 출제확률 **35%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.4

**답변:** ① 해당 **공개키를 서버 `authorized_keys`에서 즉시 제거**(키 폐기), ② **새 키쌍 발급**해 autossh 설정 갱신, ③ 터널 전용 키라 **권한을 최소화**(포트 포워딩만, 셸 접근 제한)해 피해 범위를 줄여둠. 터널 키는 일반 로그인 키와 분리해 발급하므로, 유출돼도 서버 전체 장악으로 이어지지 않게 설계했습니다.

### Q83. 동시에 여러 분석 요청이 오면 순서·격리는 어떻게 되나요?
> 출제확률 **44%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.76

**답변:** **큐 + 작업별 격리(bulkhead)** 입니다. 요청은 Celery 큐에 쌓여 **워커 동시성(concurrency)** 만큼 병렬 처리되고, 큐를 `pipeline`·`training`·`output`으로 나눠 **무거운 학습이 일반 분석을 막지 않습니다.** 작업마다 `job_id`로 상태(PipelineState)가 격리되고, prefetch=1로 한 번에 하나씩 안정적으로 가져갑니다. 즉 폭주해도 서로 간섭 없이 순차·병렬로 처리됩니다.

### Q84. 모델이 잘못된 결과를 내면 나중에 책임 추적이 되나요?
> 출제확률 **40%** · 중요도 ★★★★ · 우선순위 **B** · 준비점수 1.6

**답변:** 됩니다. ① **MLflow**에 어떤 모델·파라미터·데이터로 학습했는지 기록, ② **LangFuse**에 어떤 프롬프트·LLM이 어떤 답을 냈는지 추적, ③ **인용(citation)** 으로 결정이 KB의 어떤 지식에 기반했는지 추적, ④ **에이전트 실행 로그**(agent_runs)로 단계별 입출력 보존. 즉 "이 결과가 왜 나왔는지" 를 데이터로 역추적할 수 있습니다(설명가능성·감사성).

### Q85. 이걸 실제 상용 서비스로 키우려면 무엇이 더 필요한가요?
> 출제확률 **58%** · 중요도 ★★★★ · 우선순위 **A** · 준비점수 2.32

**답변:** 솔직히 **고가용성·확장·운영 자동화**가 다음 과제입니다 — ① 단일 VPS → **이중화·로드밸런서**(무중단), ② pgvector·MinIO → 규모 커지면 **관리형 DB·S3**로 이전, ③ GPU 1대 → **GPU 풀/오토스케일**, ④ 백업 → **다중 리전·자동 복구 리허설**, ⑤ 모니터링 → **알림(온콜)·SLO**. 다만 **컨테이너·S3 호환·git/SOPS 백업·선언적 설정**으로 이 전환이 쉽도록 미리 설계해 뒀습니다. "**지금은 저비용 MVP로 정석을 지켰고, 스케일 경로는 열려 있다**"가 핵심입니다.

## 🎤 발표 직전 30초 암기 카드 (S등급만)

1. **아키텍처**: 공인 IP 웹 서버(VPS) + GPU 로컬 서버, SSH 터널 연결.
2. **서버 2대 이유**: 값싼 클라우드는 웹, 보유 GPU는 연산 → 비용 최소·성능 확보.
3. **NAT 우회**: 로컬이 먼저 SSH로 전화 걸어 역터널, autossh로 24시간 유지.
4. **3-tier LLM**: 팀 KB(무료)→Ollama(무료)→Claude(유료), 비싼 건 최후에만.
5. **Docker**: compose + profile(core/ml/sec), 헬스체크 + 자동재시작.
6. **시크릿**: .env는 600·gitignore, .env.sops는 SOPS/age 암호화 백업.
7. **main 보호**: pre-commit→CODEOWNERS→branch protection(PR+CI 필수).
8. **백업**: Pull 방식, 1일 3회, 14일 보존, 오프사이트(학원), SHA256.
9. **회로차단**: 외부 LLM 죽어도 CLOSED→OPEN→HALF_OPEN로 폴백, Redis 공유.

> **마무리 한 문장**: "월 2~3만원에, GPU·자가치유·자동백업까지 갖춘 **저비용·고가용 인프라**를 직접 구축·운영했습니다."
